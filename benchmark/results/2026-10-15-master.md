# Benchmark results: master after #84 and #85 (2026-10-15)

Reporter built from master at ddf7099 (parallel and forkCount fixes of #82 and #83), installed locally as
`bench-local`. maven-surefire-plugin 3.6.0, JUnit 5.14.0, OpenJDK 21, Linux, 4 CPUs, 16 GB RAM.
"baseline" is the same project run with `-Pbaseline` (default surefire console reporter).
Each scenario ran twice, alternating tree and baseline; both runs are shown as `run 1 / run 2`.
Heap numbers are the highest heap left after a GC (SerialGC), as reported by `run.sh`.
For forkCount runs the fork heap is the highest among the forks.

## Comparison with 2.0.0 (same scenario as [2026-10-12](2026-10-12-v2.0.0.md))

```sh
./gen.py work/failures --classes 5000 --fail-every 2 --parallel --stack-depth 50 --msg-kb 1 --stdout-kb 1
```

| | tree 2.0.0 | tree master | baseline master |
|---|---|---|---|
| wall time | 31.5 s | 28.9 / 35.9 s | 29.8 / 38.1 s |
| Maven JVM, peak heap after GC | 182 MB | 179 / 182 MB | 185 / 192 MB |
| forked JVM, peak heap after GC | 178 MB | 178 / 177 MB | 179 / 178 MB |

No regression: the new lock around the tree and the other changes of #84 and #85 cost nothing measurable.
The spread between two runs of the same setup (29-36 s) is larger than any difference between tree and baseline.

## New: forkCount 4

```sh
./gen.py work/fork --classes 5000 --fork-count 4
./gen.py work/fork-failures --classes 5000 --fail-every 2 --fork-count 4 --stack-depth 50 --msg-kb 1 --stdout-kb 1
./gen.py work/fork-parallel --classes 5000 --fail-every 2 --parallel --fork-count 4 --stack-depth 50 --msg-kb 1 --stdout-kb 1
```

`fork-parallel` combines both: 4 forks, each running JUnit parallel classes.

| scenario | | tree master | baseline |
|---|---|---|---|
| `fork` (no failures) | wall time | 24.3 / 25.0 s | 24.1 / 24.7 s |
| | Maven JVM heap | 70 MB | 69 MB |
| | biggest fork heap | 14 / 13 MB | 14 / 13 MB |
| `fork-failures` | wall time | 39.0 / 39.5 s | 39.4 / 35.0 s |
| | Maven JVM heap | 167 / 166 MB | 167 MB |
| | biggest fork heap | 42 MB | 41 / 42 MB |
| `fork-parallel` | wall time | 41.4 / 38.6 s | 40.8 / 38.9 s |
| | Maven JVM heap | 183 / 171 MB | 171 MB |
| | biggest fork heap | 40 MB | 40 MB |

## Conclusions

- Master is on par with 2.0.0 in time and memory in the scenario measured before.
- With forkCount 4, alone or combined with JUnit parallel, the tree reporter costs no measurable time and
  at most about 10 MB of Maven heap in one `fork-parallel` run (183 vs 171 MB, 171 vs 171 MB in the other).
- All runs finished with `rc=0` and no `OutOfMemoryError`.
- With forkCount the Maven JVM is the one handling the events of every fork, so its heap does not shrink
  with more forks; the fork heaps are small because each fork has only a fraction of the classes.
