# Benchmark results: 2.0.0 (2026-10-12)

Reporter built from master at 9a7f151, whose `src/main` is identical to the `v2.0.0` tag, installed
locally as `bench-master`. maven-surefire-plugin 3.6.0, JUnit 5.14.0, OpenJDK 21, Linux, 4 CPUs, 15 GB RAM.
"baseline" is the same project run with `-Pbaseline` (default surefire console reporter).
Heap numbers are the highest heap left after a GC (SerialGC), as reported by `run.sh`.

The goal was to check [issue #49](https://github.com/fabriciorby/maven-surefire-junit5-tree-reporter/issues/49):
an `OutOfMemoryError` with many failing tests and JUnit parallel execution.

## Many failures, JUnit in parallel

```sh
./gen.py work/failures --classes 5000 --fail-every 2 --parallel --stack-depth 50 --msg-kb 1 --stdout-kb 1
```

5000 classes, 29000 tests, 14500 failing (each failure with 50 extra stack frames and a 1 KB message,
each test prints 1 KB to stdout). JUnit parallel configuration as in the issue
(`mode.default=same_thread`, `mode.classes.default=concurrent`).

| | tree 2.0.0 | baseline |
|---|---|---|
| wall time | 31.5 s | 37.6 s |
| Maven JVM, peak heap after GC | 182 MB | 190 MB |
| forked JVM, peak heap after GC | 178 MB | 178 MB |

With the Maven heap limited (`MAVEN_XMX`):

|---|---|---|
| 96 MB | OutOfMemoryError | OutOfMemoryError |
| 128 MB | OutOfMemoryError | OutOfMemoryError |
| 160 MB | OutOfMemoryError | OutOfMemoryError |

## One class with 20000 tests

```sh
./gen.py work/big --classes 1 --tests 20000 --nested-every 0
```

| | tree 2.0.0 | baseline |
|---|---|---|
| wall time, quiet (`-q`), run 1 | 40.6 s | 40.5 s |
| wall time, quiet (`-q`), run 2 | 42.1 s | 39.3 s |
| wall time, tree printed (no `-q`) | 43.9 s | 44.8 s |
| Maven JVM, peak heap after GC | 40 MB | 45-48 MB |
| forked JVM, peak heap after GC | 74 MB | 74 MB |

The tree is printed correctly (20000 lines, the last one with `'--`).

## Conclusions

- The tree reporter adds no measurable memory: the Maven JVM needs the same heap with and without it,
  and both runs fail at the same `-Xmx` limits.
- The reporter's tree does not grow. Only 6 to 11 `Node` objects are alive during the whole run, because
  each class is removed from the tree once printed, and the static maps of `TestReportHandler` are
  cleared after a class with `@Nested` classes is printed.
- The test results kept in memory are kept by surefire itself: the number of live `WrappedReportEntry`
  objects is the same in both runs.
- A single class with 20000 tests costs no measurable time. `isLastTestToBeEval` uses `indexOf`, which is
  O(N²) per class, but it is only about 2·10⁸ identity comparisons for 20000 tests.
- The thread named in issue #49, `surefire-forkedjvm-command-thread`, belongs to `CommandReader` in
  `surefire-booter`, which runs in the forked test JVM. The reporter runs in the Maven JVM and is not
  loaded in the fork, so the reported OOME did not come from the reporter. The fork heap is set with `argLine`.

## Older versions (code reading only, not measured)

Issue #49 was opened in November 2023, when the latest release was 1.2.1. 1.2.1 and 1.4.0 use the same
algorithm (the only change in `TestReportHandler` is `synchronizedMap` replaced by `ConcurrentHashMap`):

- classes without `@Nested` are printed in `testSetCompleted` and nothing is stored;
- classes with `@Nested` keep references to their entries in static maps only until the top-level class
  completes, then `cleanEntries()` removes them;
- printing one class calls `sourceNames.stream().distinct().count()` for each line, which is O(N²) in CPU and
  allocates a short-lived set the size of the class per line. A very large class prints slowly with heavy
  GC, but nothing is retained.
